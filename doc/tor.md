# Publish Bitcoin Core and the Utreexo sidecar over Tor

This setup gives Bitcoin Core and the proof sidecar stable, separately shareable
v3 onion addresses while keeping every listener on loopback. It is a manual onion
service configuration, so it does not require Bitcoin Core to access Tor's control
port.

The examples assume mainnet, Tor's SOCKS listener at `127.0.0.1:9050`, and a
systemd-based Linux host. Adjust paths and network ports for another installation.

| Shared endpoint | Tor forwards to | Service |
| --- | --- | --- |
| `BITCOIN_ONION.onion:8333` | `127.0.0.1:8334` | Bitcoin Core P2P (`NODE_NETWORK`) |
| `UTREEXO_ONION.onion:8338` | `127.0.0.1:8338` | Utreexo proof P2P (`NODE_UTREEXO`) |

Never add Bitcoin Core RPC port `8332` to an onion service. The sidecar should
continue to reach RPC locally with its cookie file.

## 1. Create the onion services

Install and start the Tor daemon using the instructions for the host operating
system. On Debian and Ubuntu, the package is normally named `tor`. Confirm that a
SOCKS listener is available at `127.0.0.1:9050`.

Merge [`contrib/tor/torrc.example`](../contrib/tor/torrc.example) into the active
`torrc`, normally `/etc/tor/torrc`. Do not put both ports under one
`HiddenServiceDir`: separate service directories produce separate onion identities.

Validate and restart Tor:

```sh
sudo tor --verify-config -f /etc/tor/torrc
sudo systemctl restart tor
sudo systemctl --no-pager --full status tor
```

Tor creates both service directories and their keys. Read the public addresses:

```sh
sudo cat /var/lib/tor/bitcoin-core/hostname
sudo cat /var/lib/tor/utreexo-sidecar/hostname
```

Only share the contents of the `hostname` files. Keep every other file in those
directories private. Back up the service keys securely if the addresses must survive
a host rebuild.

If `tor --list-modules` reports `pow: yes`, `HiddenServicePoWDefensesEnabled 1` may
be added to each service block as an additional denial-of-service defense. Verify the
configuration before enabling it because not every Tor build includes that module.

## 2. Bind Bitcoin Core for the manual service

Merge [`contrib/tor/bitcoin.conf.example`](../contrib/tor/bitcoin.conf.example) into
the existing `bitcoin.conf`. Replace
`REPLACE_WITH_BITCOIN_CORE_ONION_HOSTNAME` with the full hostname generated by Tor,
including `.onion`, and restart Bitcoin Core cleanly.

The sample deliberately provides only loopback listeners. It leaves normal outbound
IPv4/IPv6 connections direct and sends outbound onion connections through Tor. To
send *all* outbound P2P traffic through Tor, replace `onion=127.0.0.1:9050` with
`proxy=127.0.0.1:9050`. Add `onlynet=onion` as well only when all automatic peers
should be onion peers.

Do not apply the loopback-only sample unchanged if the node is intentionally meant to
remain reachable over clearnet. Operating the same node over Tor and clearnet helps
network connectivity, but the two identities may be correlated. Review Bitcoin
Core's [Tor documentation](https://github.com/bitcoin/bitcoin/blob/master/doc/tor.md)
before configuring dual reachability.

After restart, `bitcoin-cli getnetworkinfo` should list the generated onion under
`localaddresses`, and the onion network should be reachable. Bitcoin Core can relay
this address to other Bitcoin peers because it is configured with `externalip`.

## 3. Bind the sidecar to loopback

Stop the existing sidecar cleanly, then restart it with all of the same state and RPC
arguments while setting these P2P arguments:

```sh
./build/utreexo-bridge \
  --rpc-cookie=/path/to/bitcoin/.cookie \
  --online-state=/path/to/utreexo-online \
  --proof-store=/path/to/utreexo-proofs \
  --follow \
  --p2p-bind=127.0.0.1 \
  --p2p-port=8338 \
  --p2p-network=mainnet
```

Do not start two sidecars against the same online state or proof store. Wait for the
`p2p_listening` log event; the listener is started only after the sidecar has opened,
recovered, and synchronized its durable state.

The sidecar does not announce addresses or provide peer discovery. Share its onion
endpoint out of band. It serves Utreexo proofs but not ordinary headers or blocks, so
a Floresta client still needs at least one `NODE_NETWORK` peer. Current Floresta can
use the two endpoints together:

```sh
florestad \
  --proxy=127.0.0.1:9050 \
  --connect=BITCOIN_ONION.onion:8333 \
  --connect=UTREEXO_ONION.onion:8338 \
  --allow-v1-fallback
```

The fallback flag is required because this sidecar currently implements Bitcoin v1
transport only. Proofs at or before the proof store's AssumeUtreexo base are not
served; tell peers the store's base height when sharing the endpoint.

## 4. Verify before sharing

Confirm that the host has loopback listeners and no public sidecar listener:

```sh
sudo ss -ltnp | grep -E ':(8333|8334|8338)[[:space:]]'
```

Expected listeners are `127.0.0.1:8333`, `127.0.0.1:8334`, and
`127.0.0.1:8338`. There should be no `0.0.0.0:8338` or `[::]:8338` listener.
No router port-forward or inbound firewall opening is needed for an onion service.

Test both public endpoints through Tor, preferably from a second host:

```sh
torsocks nc -vz BITCOIN_ONION.onion 8333
torsocks nc -vz UTREEXO_ONION.onion 8338
```

A TCP check establishes reachability but does not validate the application protocol.
For an end-to-end test, connect a Tor-enabled Bitcoin Core peer to the first endpoint
and a current Floresta instance to both endpoints. On the serving host, verify the
Core connection with `bitcoin-cli getpeerinfo` and look for `p2p_peer_version` in the
sidecar debug log.

Tor's onion-service setup guide documents service directories, key handling, and
multiple independent services: [Set up your Onion Service](https://community.torproject.org/onion-services/setup/).
